# API Contracts

Both backend services publish OpenAPI specs — don't hand-edit the generated files below,
regenerate them instead.

| Boundary | Spec | Generated by |
|---|---|---|
| React ↔ Java backend | [api/backend.openapi.json](api/backend.openapi.json) | springdoc-openapi (`backend`), served at `/v3/api-docs` |
| Java backend ↔ ml-service | [api/ml-service.openapi.json](api/ml-service.openapi.json) | FastAPI auto-generated, served at `/openapi.json` |

## Shared conventions (both boundaries)

**Correlation ID**: every request carries `X-Correlation-Id`. The frontend generates one if
absent; each backend forwards it downstream and includes it in every log line.

**Error shape** (both `backend` and `ml-service`):

```json
{
  "code": "MODEL_INFERENCE_FAILED",
  "message": "Human-readable message",
  "details": { "field": "optional structured context" }
}
```

## `ml-service` diagnosis endpoint (contract summary)

`POST /agent/diagnose` — `X-Correlation-Id` is a header (per the shared convention above),
not a body field.

Request:
```json
{
  "symptoms": { "fever": true, "appetite_loss": true, "...": "..." },
  "image_url": null
}
```

Response (`200`):
```json
{
  "diagnosis": "Foot and Mouth Disease",
  "confidence": 0.82,
  "explanation": "Based on the fever, mouth lesions, and excessive salivation observed, this points strongly toward Foot and Mouth Disease...",
  "recommended_action": "escalate_to_vet",
  "sources": []
}
```

`recommended_action` is one of `escalate_to_vet` (always, for reportable/contagious
diseases — see [docs/DISCLAIMER.md](DISCLAIMER.md), regardless of confidence),
`consult_vet` (uncertain diagnosis, or any other diagnosed disease), or `monitor`
(`"Healthy"` only). `sources` is `[]` until M6 wires up RAG.

`explanation` is generated by an LLM (M5, `app/agent/llm.py` — provider/model configurable,
local Ollama by default, never hardcoded to one provider) when one is reachable, grounded
strictly in the diagnosis/confidence/top-features already computed — never a source of new
medical claims. Falls back to a fixed template (`"Predicted X with Y% confidence, based
primarily on: ..."`) if the LLM call fails for any reason — callers should not assume any
particular explanation format, only that the field is always a non-empty string.

**Known error codes**: `MODEL_NOT_TRAINED` (`503`) — the model artifact isn't present;
train it via `python -m training.symptom_model_train` in `ml-service/`. `NOT_IMPLEMENTED`
(`501`) — `image_url` was provided; image-based prediction isn't built yet (M5+).

## `backend` endpoints (contract summary, M3)

`POST /api/cattle` — create a cattle record.

Request: `{"tagNumber": "COW-001", "farmId": 42}`
Response (`201`): `{"id": 1, "tagNumber": "COW-001", "farmId": 42, "createdAt": "..."}`

`POST /api/cattle/{cattleId}/diagnoses` — submit symptoms for a cattle, calls `ml-service`,
persists the result.

Request: `{"symptoms": {"fever": true, "...": "..."}}`
Response (`201`):
```json
{
  "id": 7,
  "cattleId": 1,
  "diagnosis": "Foot and Mouth Disease",
  "confidence": 0.81,
  "explanation": "...",
  "recommendedAction": "escalate_to_vet",
  "createdAt": "..."
}
```
Note: `explanation` is returned live from `ml-service` but not persisted — `diagnosis_case`
has no column for it (see `docs/DECISIONS.md`).

**New error codes** (backend, via `ApiException`): `CATTLE_NOT_FOUND` (`404`),
`CATTLE_TAG_DUPLICATE` (`409`), `ML_SERVICE_UNAVAILABLE` (`503`, connection failure to
ml-service), `ML_SERVICE_ERROR` (`502`, ml-service returned an error response).
